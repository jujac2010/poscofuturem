# 단일 사업장 지게차 엔진 과열 조기경보 PoC 설계

## 1. 목적

동일 모델 지게차 5대가 운영되는 한 개 사업장에서 3개월 동안 운행·ECU·위치 데이터를 안정적으로 축적하고, 엔진 과열 징후를 고신뢰로 조기 탐지하여 정비 담당자의 점검 우선순위를 지원한다.

이번 PoC는 과거 고장 이력과 통제된 이상시험이 없는 조건에서 수행된다. 따라서 초기 결과를 확정적인 고장 확률이나 검증된 48시간 예측 모델로 표현하지 않는다. 제품의 1차 메시지는 다음과 같다.

> 향후 48시간 내 엔진 과열 위험을 관찰할 필요가 있는 장비를 근거와 함께 제시하고, 정비 조치 결과를 향후 예측 모델 학습 데이터로 축적한다.

## 2. 목표와 성공 기준

### 목표

- 지게차 5대의 데이터 수집·정규화·품질 상태를 지속적으로 확인한다.
- 차량별 정상 운행 기준선과 동일 모델 차량 간 편차를 계산한다.
- 단일 센서의 일시적 변동을 경보로 승격하지 않고, 복수 근거가 지속될 때만 정비 경보를 생성한다.
- 정비 담당자가 경보 근거를 확인하고 점검·조치·결과를 기록할 수 있게 한다.
- 3개월 후 정상·이상·정비 결과가 연결된 분석 이력을 확보한다.

### 초기 합격 기준

- 정상 운영 구간에서 표준화된 텔레메트리 데이터 완성도 95% 이상
- 데이터 수집 중단·지연·센서 오류를 운영 화면에서 식별 가능
- 모든 정비 경보가 장비, 시각, 근거, 신뢰도, 조치 이력과 연결됨
- 동일 원인으로 열린 경보가 반복 생성되지 않음
- 정비 담당자가 경보를 확인하고 실제 조치 결과를 기록 가능
- 3개월 종료 시점에 모델 학습에 사용할 수 있는 원천 데이터·특징량·라벨 이력 제공

실제 과열 사례가 없으면 예측 정밀도·재현율을 합격 기준으로 확정하지 않는다. 해당 지표는 실제 과열 또는 정비 확인 사례가 축적된 후 산출한다.

## 3. 범위

### 포함

- 한 개 사업장, 동일 모델 지게차 5대
- 엔진 과열 징후 조기경보
- ECU·위치 데이터 수집 어댑터 구조
- 시뮬레이터 및 CSV/JSON 파일 기반 초기 입력
- 데이터 품질·기준선·경보 상태 표시
- 정비 담당자용 경보 확인 및 조치 기록
- 3개월 데이터 보관과 모델 학습용 라벨 생성
- 정상, 누락, 지연, 이상값, 네트워크 단절 테스트

### 제외

- 다사업장 통합 관제
- 자동 운전 제한 또는 차량 제어
- 모바일 앱 및 외부 알림 채널
- 여러 고장 유형의 동시 예측
- 실제 프로토콜이 결정되기 전의 특정 CAN·MQTT·OPC-UA 구현
- 통제된 과열 재현 시험
- 확정적인 고장 확률 또는 검증 완료된 48시간 ML 모델

## 4. 사용자와 업무 흐름

주 사용자는 정비 담당자다. 작업자와 관리자는 초기 PoC의 필수 사용자 흐름에 포함하지 않으며, 향후 권한·화면 확장의 대상으로 둔다.

```text
경보 발생
  -> 정비 담당자 확인
  -> 장비 점검 지시
  -> 점검 결과와 조치 입력
  -> 재운행 또는 추가 정비 결정
  -> 실제 이상 여부와 결과를 학습 라벨로 저장
```

초기 알림 채널은 대시보드 내 경보 대기열로 한정한다. 외부 메시지·메일·모바일 푸시는 수집 방식과 운영 책임자가 확정된 후 별도 설계한다.

## 5. 시스템 아키텍처

```text
ECU / 위치 / 파일 / 시뮬레이터
          |
          v
   수집 어댑터 계층
          |
          v
현장 게이트웨이: 임시 저장·재전송·연결 상태
          |
          v
정규화·품질 검사: 단위·시각·중복·범위·누락
          |
          +--> 원천 텔레메트리 보관
          |
          v
기준선·특징량 계산: 차량별 정상·동종 차량 편차
          |
          v
고신뢰 경보 엔진
          |
          +--> 경보·근거·상태 이력
          |
          v
정비 담당자 화면 --> 조치 결과·실제 이상 라벨
```

### 구성요소 경계

#### 수집 어댑터

각 원천 시스템의 연결 방식과 장비별 필드명을 표준 입력으로 변환한다. 다음 인터페이스를 유지한다.

```ts
interface EcuAdapter {
  connect(): Promise<void>;
  readBatch(): Promise<RawTelemetry[]>;
  health(): Promise<SourceHealth>;
  close(): Promise<void>;
}
```

초기 구현은 `SimulatorAdapter`와 `FileReplayAdapter`로 시작한다. 실제 현장 프로토콜이 결정되면 해당 프로토콜 어댑터를 추가하며, 기준선·경보·화면 모듈은 변경하지 않는다.

#### 현장 게이트웨이

네트워크가 일시적으로 끊겨도 원천 데이터를 임시 저장하고 연결 복구 후 순서대로 재전송한다. 게이트웨이는 수집 시각과 수신 시각을 모두 기록하여 지연과 데이터 손실을 구분한다.

#### 정규화·품질 검사

단위 변환, 장비 ID 매핑, 시간대 통일, 중복 제거, 허용 범위 검사, 누락 표시를 수행한다. 원천값을 덮어쓰지 않고 원천 데이터와 표준 데이터를 분리한다.

#### 기준선·특징량 계산

초기 안정화 구간의 정상 운행 데이터를 바탕으로 차량별 온도 범위·상승률·부하 관계를 계산한다. 이후 기준선은 새 데이터로 천천히 갱신하되, 경보 또는 정비 구간의 데이터는 정상 기준선 학습에서 제외한다.

#### 경보 엔진

표준 텔레메트리와 특징량을 입력으로 받아 위험 단계, 근거, 신뢰도, 경보 상태를 반환한다. 경보 엔진은 UI나 특정 수집 프로토콜에 의존하지 않는다.

## 6. 데이터 모델

### TelemetrySnapshot

- `assetId`: 지게차 식별자
- `observedAt`: 장비에서 측정된 시각
- `receivedAt`: 플랫폼이 수신한 시각
- `engineCoolantTemperature`
- `engineOilTemperature`
- `engineRpm`
- `loadRate`
- `engineHours`
- `ambientTemperature`
- `latitude`, `longitude`, `speed`
- `sourceType`
- `qualityStatus`

센서가 제공되지 않는 필드는 null로 저장하고, 추정값으로 대체하지 않는다.

### DataQuality

- 수신 지연 시간
- 최근 정상 수신 시각
- 누락 필드 목록
- 범위 초과 필드 목록
- 중복·시간 역전 여부
- 전체 신뢰도

### BaselineProfile

- 장비별 정상 온도 범위
- 부하·RPM·외기온도 조건별 정상 범위
- 정상 상승률 및 지속시간 기준
- 동일 모델 차량군의 중앙값과 편차
- 기준선 버전과 적용 기간

### RiskAssessment

- 위험 단계: `NORMAL`, `OBSERVE`, `CAUTION`, `MAINTENANCE_ALERT`, `DATA_ISSUE`
- 위험 점수와 점수 산출 근거
- 기준선 대비 초과량
- 상승 지속시간
- 동종 차량 대비 편차
- 데이터 신뢰도
- `observedWindow`: “향후 48시간 관찰 구간”
- 경보 생성·확인·종료 시각

### MaintenanceAction

- 경보 ID와 장비 ID
- 담당자와 확인 시각
- 점검 내용
- 조치 내용
- 부품 교체 여부
- 재운행 가능 여부
- 실제 과열 징후 여부
- 종료 사유

## 7. 고신뢰 경보 로직

초기 판정은 다음 신호를 조합한다.

- 엔진·냉각계통 온도의 절대값 초과
- 온도 상승률 증가
- 상승 상태의 지속시간
- 부하·RPM 증가와 온도 상승의 동시성
- 동일 모델 5대 기준선 대비 편차
- 센서 품질과 데이터 완성도

판정 단계는 다음과 같다.

- `NORMAL`: 기준선 내이며 품질 양호
- `OBSERVE`: 단일 신호의 상승 또는 일시적 차량 편차
- `CAUTION`: 두 개 이상의 신호가 정해진 시간 동안 지속
- `MAINTENANCE_ALERT`: 온도 절대값, 상승률, 지속시간, 차량 편차 중 세 가지 이상이 충족되고 데이터 신뢰도가 충분함
- `DATA_ISSUE`: 수집 중단, 센서 이상, 과도한 지연 또는 핵심 필드 누락

동일 경보가 열린 동안에는 새 경보를 만들지 않고 기존 경보의 근거와 지속시간만 갱신한다. 경보 종료 후 동일 원인이 재발하면 새 이벤트로 기록한다.

초기 화면에서는 `MAINTENANCE_ALERT`를 “향후 48시간 내 과열 위험 관찰 구간”으로 표시한다. 실제 과열·정비 라벨이 충분히 확보되면 같은 입력 계약을 유지한 채 통계 모델 또는 ML 모델로 판정 모듈을 교체한다.

## 8. 데이터 저장과 보관

1초 단위 원천 데이터를 3개월간 모두 운영 DB에 저장하면 불필요하게 큰 저장량이 발생할 수 있다. 따라서 다음 보관 계층을 사용한다.

- 원천 데이터: 게이트웨이 또는 파일 저장소에 배치 보관
- 운영 DB: 10초·1분 집계값, 특징량, 기준선, 경보, 정비 이력 저장
- 장기 분석: 원천 데이터와 표준 데이터의 기간별 파일 보관

원천 데이터에는 `assetId`, `observedAt`, `receivedAt`, `sourceType`, 원천 payload hash를 포함해 재처리와 중복 검증이 가능해야 한다.

## 9. 오류·안전 처리

- 수신 중단은 위험 경보로 오인하지 않고 `DATA_ISSUE`로 표시한다.
- 센서값이 허용 범위를 벗어나면 해당 필드를 격리하고 경보 신뢰도를 낮춘다.
- 핵심 필드가 누락되면 위험 단계는 승격하지 않는다.
- 시간 역전·중복 데이터는 저장 전에 제거하되 원천 payload는 보존한다.
- 기준선 학습에서 경보·정비 구간 데이터를 제외해 오염을 방지한다.
- 경보 근거 없는 단일 점수만으로 정비 경보를 생성하지 않는다.
- 모든 경보 상태 변경과 정비 조치는 변경 이력으로 남긴다.

## 10. 화면 구성

초기 운영 화면은 다음 네 영역으로 구성한다.

1. 현장 요약: 5대 상태, 데이터 수신 상태, 열린 경보 수
2. 경보 대기열: 위험 단계, 장비, 근거, 최근 수신 시각, 우선순위
3. 지게차 상세: 온도·부하·RPM 추이, 기준선 비교, 위치·운행 정보
4. 정비 이력: 확인·점검·조치·실제 이상 여부와 재운행 결과

시각적 상태는 색상만으로 구분하지 않고 단계명·점수·근거 문구를 함께 표시한다.

## 11. 검증 계획

### 단위·통합 검증

- 정상 텔레메트리로 기준선이 안정적으로 생성되는지 확인
- 절대값·상승률·지속시간·차량 편차 조합별 위험 단계 확인
- 단일 신호가 경보로 승격되지 않는지 확인
- 동일 경보 반복 억제 확인
- 누락·지연·범위 초과·시간 역전 데이터 처리 확인
- 수집 중단과 복구 후 재전송 확인
- 정비 결과가 학습 라벨과 경보에 연결되는지 확인

### 재생 기반 검증

실제 과열을 유발하지 않고, 정상 데이터에 과열 징후 패턴을 삽입한 재생 데이터를 사용해 경보 파이프라인과 화면을 검증한다. 이 테스트는 시스템 동작 검증용이며 실제 현장 예측 성능의 증거로 사용하지 않는다.

### 3개월 운영 평가

- 데이터 완성도
- 장비별 기준선의 안정성
- 경보 수와 정비 확인 결과의 일치 정도
- 미확인 경보 비율
- 중복·지연·데이터 이상 건수
- 향후 모델 학습에 사용할 수 있는 라벨 수와 품질

## 12. 단계별 전환

### 1단계: 연결 전 검증

시뮬레이터와 파일 재생으로 표준 데이터 계약, 품질 검사, 기준선, 경보, 정비 기록을 검증한다.

### 2단계: 현장 수집 시작

실제 프로토콜이 확정되면 해당 어댑터와 게이트웨이를 연결하고, 초기 안정화 구간에서 기준선을 생성한다. 이 단계의 화면은 경보보다 데이터 품질과 수집 안정성을 우선 표시한다.

### 3단계: 고신뢰 경보 운영

정비 담당자가 경보를 확인하고 조치 결과를 기록한다. 경보 기준은 실제 운영 피드백으로 조정하되, 변경 이력과 기준선 버전을 보존한다.

### 4단계: 예측 모델 검토

3개월 데이터에서 충분한 이상·정비 라벨이 확보되었을 때만 48시간 예측 모델을 별도 검증한다. 라벨이 부족하면 모델 도입을 보류하고 기준선·이상탐지 방식을 유지한다.

## 13. 향후 확장 경계

이 설계는 이후 다음 확장을 지원한다.

- 실제 CAN·MQTT·OPC-UA·REST 어댑터 추가
- 작업자·관리자·정비 담당자 권한 분리
- 다사업장·장비군 비교
- 외부 알림 채널
- 고장 유형별 모델 분리
- 모델 버전·설명 가능성·승인 이력 관리

확장 기능은 이번 단일 사업장 엔진 과열 PoC의 성공 여부와 데이터 품질이 확인된 후 별도 설계한다.
